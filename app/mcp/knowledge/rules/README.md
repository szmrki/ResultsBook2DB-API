# 競技規則の変遷データ（rules/）

rb2db の利用者が「ある大会がどの規則で行われたか」「規則変更をまたいで比較してよいか」を
すぐ確認できるようにするための構造化データ。**このディレクトリの YAML が唯一の情報源**で、
利用者向けの `rules.md`（MCP リソース・`/v1/notes`）や API の応答はここから生成する。

> 状態: 叩き台（2026-10-18）。`verified: false` の項目は原文との照合が済んでいない。

---

## 1. 対象範囲

**判断基準: 変更の前後で、Results Book に記録される値や分布、またはその解釈が変わりうるか。**

規則として競技に関わっていても、記録に表れないもの（まれな反則への罰則、手続きの細かな変更など）は含めない。

| カテゴリ（`category`） | 含めるもの |
|---|---|
| `board`（盤面と投球） | フリーガードゾーン、ノーティック、MD の事前配置ストーン、パワープレー |
| `scoring`（得点とハンマー） | ブランクエンド後のハンマー、エキストラエンド、ハンマーの決め方（LSD / DSC） |
| `format`（試合形式） | エンド数、コンシードの条件 |
| `time`（時間） | 持ち時間、タイムアウト |

**対象外**: 服装、コーチ・チーム役員、ドーピング、選手資格、クラス分け、審判の手続き、
大会運営の細則（総当たりやプレーオフの方式など）、条文の言い回し・書式だけの修正、
まれな反則への罰則（スウィーピング違反、動いているストーンへの接触など）、選手の欠員・交代の手続き、
スウィーピングとブラシの規定（Results Book だけでは効果を分析できず、映像などとの組み合わせが必要なため）、
車いすカーリング（rb2db に収録がないため）。

迷ったら「この変更を知らないと、集計結果を誤って解釈しうるか」で判断する。
除外と判断した変更は、同じ検討を繰り返さないよう `editions.yaml` の `notes` に理由とともに残す。

## 2. ファイル構成

| ファイル | 中身 | 1レコードの単位 |
|---|---|---|
| `sources.yaml` | 原典（PDF）の台帳。元の URL・Wayback の URL | 文書1つ |
| `editions.yaml` | 規則書の版と、その収録状況 | 版1つ |
| `topics.yaml` | ルールの概念（版をまたいで変わらない ID） | 概念1つ |
| `changes.yaml` | 版ごとの変更点 | 変更1件 |

将来追加するもの（段階 2）: 大会と版の対応づけ。`events` に開始日を追加する
szmrki/ResultsBook2DB#30 が済めば、開始日と各版の `effective_from` の比較で対応づける。
それまでの代わりとして `series_months.yaml`（大会シリーズの通常開催月）と
`event_overrides.yaml`（例外の大会と版の対応）を使う案もある。

原典の PDF そのものは**リポジトリに置かない**（著作権のため）。台帳には URL だけを書く。
手元の PDF は gitignore 済みの `sources/rules/<publisher>/<元のファイル名>` に置く
（例: `sources/rules/wcf/Rules2026-ChangeLog.pdf`、`sources/rules/jca/rule-2025-09-01-37.pdf`）。
ファイル名は台帳の `url` の末尾（分割版は `parts`）と一致させ、台帳から機械的にたどれるようにする。

## 3. 書き方の約束

### 版（`editions.yaml`）

- `id` は WCF の版の年（例: `wcf-2026`）。JCA の日本語版は `jca_edition` に年月で持つ（例: `2026.09`）。
- `document_date` は規則書の表紙の日付（月までしか書かれていない版は `YYYY-MM`）。`effective_from` は施行日で、本文に明記がなければ
  `effective_from_basis` に根拠（`cover_date` など）を書く。
- `coverage` は収録状況。「書いていない＝変更なし」と誤読されないために必ず書く。
  - `full`: 全変更点を確認済み
  - `major_only`: 主要トピックだけ確認済み（古い版向け）
  - `drafted`: 下書き済みで、人の確認待ち（除外の判断を含む）
  - `pending`: 原典はあるが未着手
  - `missing`: 原典が見つかっていない

### 概念（`topics.yaml`）

- `id` は英小文字のスネークケース。**条番号に依存させない**（版ごとに番号が変わるため）。
- 粒度は「〜のルールはどう変わった？」と聞かれる単位。条・項の単位まで細かくしない。
- **4 人制と MD で規則の中身が違うものはトピックを分ける**（例: フリーガードゾーンと MD の序盤の除去制限、
  ブランクエンド後のハンマー）。`both` は同じ規定が両方に当てはまるとき（持ち時間の条など）だけに使う。
  こうしておくと、トピックの対象がそのまま変更の対象になる。
- 新しく導入された概念も、導入された時点で ID を付ける（`changes.yaml` に `type: introduced` で記録）。
- 分割・統合されたときは、`changes.yaml` に `type: split` / `merged` と `related_topics` で記録する。

### 変更点（`changes.yaml`）

- `summary_ja` は**自分の言葉で要約する**。原文を長く引用しない。
- `data_impact` には「このデータで何に気をつけるか」を書く。**分析結果（未発表の知見）は書かない。**
- `source` に版・文書・条番号・ページを必ず書く。
- `verified` は、人が原文と照らして確認したら `true` にする。

## 4. 作り方の手順

1. 原典を集め、`sources.yaml` に登録する（WCF の規則書と「Showing Changes」版）。
2. 「Showing Changes」版から変更箇所を抜き出す（黄色＝追加、赤の取り消し線＝削除）。
3. 対象範囲（§1）に入るものだけを `changes.yaml` に下書きする（LLM に下書きさせてよい）。
4. 人が原文と照らし、`verified: true` にする。
5. その版の `coverage` を更新する。
6. `uv run python scripts/generate_rules_md.py` で `app/mcp/knowledge/rules.md` を生成し直す。
   `rules.md` は MCP リソース `rb2db://rules` と `/v1/notes/rules` で配信される。直接編集しないこと。

一次情報源は WCF 英語版。JCA 日本語版は用語の確認や、WCF 版が見つからない年の補完に使う。
